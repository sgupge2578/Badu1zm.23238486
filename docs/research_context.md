## 研究の概要

- 題目: 生成AIを用いたソフトウェア企画案の発散支援に関する研究 ― IRに基づく問題分割と外部情報源を利用した企画案生成 ―

- 先行研究: 谷口雄偲「AIとの対話を通じた問題発見ツール」（佐賀大学理工学部卒業論文, 2026）。問題意識抽出と根拠付与の2工程を実装し、その結果を IR として出力する。

## 研究全体の中での位置づけ

ソフトウェア企画支援AIツールは7工程からなる。

問題意識抽出 → 根拠付与 → **発散（本研究）** → 収束 → 試作 → 評価 → 企画書生成

- 入力: 先行研究が出力した IR のうち、根拠付与まで完了したレコード（`stage=evidence`）
- 出力: ソフトウェア企画案（JSON / Markdown）。後続の評価・収束工程が読み込む

## 研究目的

IR を入力として、**利用者の問題意識との整合性を保ちながら**、複数の観点からソフトウェア企画案を発散的に生成する支援モジュールを構築する。

## 設計の中心となる考え方

1. **IR との整合性（トレーサビリティ）が最優先。** 企画案の数や新規性よりも、「どの問題に対し、どの根拠・制約・文献を踏まえて生成されたか」を追跡できることを重視する。すべての中間結果に、元の IR との対応情報を持たせる。
2. **IR を検索の最小単位にしない。** 1つの IR には時間不足・家事負担・心理的負担など複数の問題が混在する。IR 全体から検索語を作ると特定の観点に偏るため、外部情報源を検索する前に IR を部分問題へ分割する。
3. **問題分割エージェントは解決策を出さない。** 役割は「検索対象の整理」に限定する。「時間がない → 自動スケジュールアプリ」のように検索前に解決方向を固定すると、外部情報から新しい発想を得る余地がなくなるため。
4. **分割パターンは複数生成する。** 分割方法を1つに固定すると探索が偏るため、異なる観点（時間制約中心・矛盾中心・心理的負担中心など）のパターンを複数作る。
5. **問題分割にはルールベースの代替を持たせない。** LLM 由来とルール由来の出力が混ざると、LLM の振る舞いを評価できなくなるため。
6. **外部情報は発想の材料であり、そのまま転用しない。** 文献の知見を「アイデアの種」として抽出し、IR の問題に適用する。
7. **処理単位でファイルを分ける。** 処理の差し替えや比較を容易にするため。新しい処理は既存ファイルを肥大化させず、独立したファイルとして追加する。
8. **LLM 出力の変動を前提にする。** 1回の実行結果で設計の妥当性を判断しない。評価は同一条件での複数回実行を前提とする。

## IR の主な項目と発散モジュールでの使い方

| IR 項目 | 内容 | 発散モジュールでの利用 |
|---|---|---|
| target_user | 対象ユーザー | 部分問題の対象範囲、企画案の想定利用者 |
| problem | 課題 | 部分問題の中心的な記述、検索意図の起点 |
| contradiction | 両立しにくい条件・矛盾 | 矛盾・トレードオフ観点の分割パターン |
| objective | 達成したい状態 | 企画案が目的から外れていないかの確認 |
| value | 得られる価値 | 企画案の提供価値との対応確認 |
| 背景・根拠（explanation） | 場面、行動、感情、判断理由、制約 | 部分問題の制約条件、検索意図の具体化 |

## これまでの経緯

1. **段階1: 手動 CSV による最小パイプライン。** IR＋文献 → アイデアの種 → 企画案5件。データフローを先に確認した。課題は、文献を人手で用意する必要があること。
2. **段階2: CiNii Research API による自動検索。** IR から検索語を生成（日本語9件・英語9件）。上位4語のうち3語が0件で、取得できた2件はどちらも「家事の効率化」由来だった。IR には時間・栄養・心理・親子関係が含まれるのに、外部情報は一側面に偏った。
3. **段階3: 問題分割AIエージェントの導入。** 同一 IR から3つの分割パターン（DP-001 時間制約中心／DP-002 矛盾・トレードオフ中心／DP-003 心理的負担中心、部分問題 計7件）が生成されることを確認した。

## 実装状況

| 処理 | 状態 | 残っている作業 |
|---|---|---|
| IR 読み込み | 実装済み | stage や session_id による選択条件の整理 |
| 問題分割 | 実装済み | 複数 IR・複数試行での妥当性の確認 |
| 分割パターンの選択 | 未実装 | 利用者による確認・選択機能 |
| 検索語生成 | SubProblem 対応済み（条件C） | 部分問題ごとの検索・文献との対応付け（作業3） |
| 外部情報源検索 | CiNii で実装済み | 部分問題との対応情報の保存、取得件数の改善 |
| 文献フィルタリング | 未実装 | 部分問題との関連性による選別 |
| アイデアの種抽出 | 実装済み | 部分問題との対応情報の付与 |
| 企画案生成 | 実装済み | 複数の部分問題を統合する案の生成方法 |
| 簡易評価 | 未実装 | 評価観点の確定と評価理由の出力 |

**接続状況:** 問題分割の結果は検索語生成まで渡るようになった（作業1、`--condition C`）。ただし文献検索・アイデアの種・企画案生成は、まだ部分問題との対応を保持していない（作業3・5・6）。

## 今後の作業計画（実施順）

| 順序 | 作業内容 | 完了の判断基準 |
|---|---|---|
| 1 | keyword_generator の SubProblem 対応 | 部分問題ごとに異なる検索語が生成される |
| 2 | 分割パターンの確認・選択機能 | 利用者が選んだ分割だけが後続へ渡る |
| 3 | 検索結果への部分問題・検索語の対応情報の付与 | 取得文献から検索経路を逆にたどれる |
| 4 | 文献フィルタリング | 除外された文献と除外理由が保存される |
| 5 | アイデアの種への部分問題対応情報の付与 | 種から部分問題と文献を特定できる |
| 6 | 企画案生成の入力への部分問題の追加 | 企画案が対象部分問題を保持する |
| 7 | 簡易評価の実装 | IR 項目ごとの適合判定と理由が出力される |
| 8 | 条件 A・B・C の比較実験 | 同一 IR で三条件を複数回実行し、結果を集計できる |

実装は、中間データの対応関係を保持する部分から順に進める。評価段階で中間結果を記録していないと、実験をやり直すことになるため。

### 各作業の注意点

- **検索語生成（1）:** SubProblem の name・description・search_intent・constraints を入力にする。0件になった検索語は利用者の発話に近い表現だったため、研究文献で使われる表現・類義語・上位概念に変換する。ただし制約条件（例: 「平日夕方」）は検索語から落ちやすいので、部分問題側に保持し、文献の評価時に使う。
- **検索結果（3）:** 「IR → 分割パターン → 部分問題 → 検索語 → 文献」の対応を保持する。複数の部分問題から同じ文献が取れた場合の重複除去方法を決める。
- **アイデアの種（5）:** 文献と種を一対一に固定しないデータ構造にする（1文献から複数の部分問題に対応する種が出得る）。抽出項目は固定辞書にせず、search_intent に基づいて LLM に要約させる。
- **簡易評価（7）:** 収束工程とは別物で、企画案が元の問題意識から外れていないかの基本チェック。数値指標（IR 項目と企画案のコサイン類似度など）と理由付き判定を併用する。類似度が高いことは表現が近いことを示すだけで、問題の解決を保証しない点に注意。
- **比較実験の前提（8）:** 作業8の前に、条件Bの辞書語による補強を外し、条件Cとそろえる（比較の公平性のため）。現在、条件Bは LLM が生成した検索語の後ろに辞書変換の語を足しているが、条件Cは LLM の出力だけを使っている。
- **コスト:** 部分問題ごとに検索すると、API と LLM の呼び出し回数が部分問題数に比例して増える。実行時間と料金も評価の検討事項に含める。

## 評価実験の設計

| 条件 | 処理構成 | 確認できること |
|---|---|---|
| A | IR → 企画案生成 | 外部情報を使わない場合の基準 |
| B | IR → 検索語 → 外部文献 → 種 → 企画案 | 外部情報利用の影響（A と比較） |
| C | IR → 問題分割 → 部分問題 → 検索語 → 外部文献 → 種 → 企画案（提案） | 問題分割の影響（B と比較） |

- 評価観点の候補: 企画案の多様性、IR との整合性、部分問題の網羅性、新規性、実現可能性
- 特に重視: 「複数の異なる問題観点を扱っているか」と「外部情報を使っても元の目的・課題・根拠から外れていないか」。この2つは相反し得るため、片方だけを高めても目的は達成されない。
- 既存の評価ツール: 先行研究のコサイン類似度・正規化エントロピーの評価ツールを引き継いで再利用する予定。
- 条件 A・B・C はすべて同一の入力 IR で実行できる状態にしておく。
